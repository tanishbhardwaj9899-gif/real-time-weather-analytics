# Real-Time Weather Analytics System

real-time data streaming project that collects weather information from multiple European cities, streams events
through Apache Kafka, processes and validates the data with Python and
Pandas, stores the results in PostgreSQL, and presents weather insights
in a Streamlit dashboard.

## Project Overview

The system is designed to demonstrate an end-to-end data streaming
pipeline:

Open-Meteo API
      |
      v
Kafka Producer
      |
      v
Apache Kafka (weather_data topic)
      |
      v
Kafka Consumer / Data Processor
      |
      +----> Data validation and transformation (Pandas)
      |
      +----> PostgreSQL (weather_analytics)
      |
      v
Streamlit Dashboard

### Main objectives

-   Collect current weather observations for multiple cities.
-   Publish weather events to Kafka.
-   Consume and process streaming events.
-   Validate weather values and transform the data using Pandas.
-   Store processed records in PostgreSQL.
-   Visualize weather conditions and trends in a Streamlit dashboard.
-   Evaluate the pipeline using performance measures such as throughput,
    latency, reliability, and data accuracy. Scalability can be
    evaluated by increasing the number of cities, event volume, or
    consumers and observing system behaviour.

## Data Source

This project uses the [Open-Meteo API](https://open-meteo.com/). The
producer reads city names and coordinates from
`producer/europe_cities.csv` and requests weather information for those
locations.

Typical fields used by the pipeline include:

-   `city`
-   `latitude` and `longitude`
-   `temperature`
-   `humidity`
-   `feels_like`
-   `wind_speed` and `wind_direction`
-   `precipitation`
-   `weather_code`
-   `timestamp` --- the weather observation time
-   `produced_at` --- the time the producer created the event

The observation `timestamp` and event `produced_at` have different
meanings and should not be substituted for one another.

Check the Open-Meteo documentation and usage limits before collecting
data at large scale. Respect API rate-limit responses such as HTTP 429
and any supplied `Retry-After` value.

## Installation and Setup

### 1. Clone or open the project

Open the project folder in a terminal:

``` powershell
cd "C:\Users\spider\OneDrive\Desktop\real time weather analytics"
```

If you have cloned the repository to a different location, use that
folder path instead.

### 2. Create and activate a virtual environment

``` powershell
python -m venv venv
.\venv\Scripts\Activate.ps1
```

If PowerShell blocks activation, you can use Command Prompt:

``` cmd
venv\Scripts\activate.bat
```

### 3. Install Python dependencies

``` powershell
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

requirements.txt is there and contains all the dependencies you needed if not 
you can install packages using terminal:

``` powershell
python -m pip install kafka-python pandas requests psycopg2-binary python-dotenv streamlit plotly
```

After confirming the environment works, update `requirements.txt`:

``` powershell
python -m pip freeze > requirements.txt
```

### 4. Configure PostgreSQL

Create a PostgreSQL database named:

``` sql
CREATE DATABASE weather_analytics;
```

Create a `.env` file in the project root:

``` env
DB_HOST=localhost
DB_NAME=weather_analytics
DB_USER=postgres
DB_PASSWORD='YOUR_POSTGRES_PASSWORD'
DB_PORT=5432
```

Replace `YOUR_POSTGRES_PASSWORD` with your local PostgreSQL password. Do
not commit `.env` or publish database credentials.

The application expects a `weather_records` table with the following
structure:

``` sql
CREATE TABLE IF NOT EXISTS weather_records (
    id BIGSERIAL PRIMARY KEY,
    city VARCHAR(100) NOT NULL,
    latitude DOUBLE PRECISION,
    longitude DOUBLE PRECISION,
    temperature DOUBLE PRECISION,
    humidity DOUBLE PRECISION,
    feels_like DOUBLE PRECISION,
    wind_speed DOUBLE PRECISION,
    wind_direction DOUBLE PRECISION,
    precipitation DOUBLE PRECISION,
    weather_code INTEGER,
    temperature_category VARCHAR(50),
    timestamp TIMESTAMP NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

If the table already exists, do not create it again unnecessarily. You
can inspect its columns with:

``` sql
SELECT column_name, data_type
FROM information_schema.columns
WHERE table_name = 'weather_records'
ORDER BY ordinal_position;
```

### 5. Start Kafka

Start your Kafka broker using the Docker Compose configuration supplied
with your Kafka setup. The current Python producer and consumer are
configured to connect to:

``` 
localhost:9092
```

Make sure the broker is running and that the `weather_data` topic is
available. The exact Docker command depends on the Compose file and
Kafka image/configuration used in your environment.

## Running the Pipeline

Run each component in a separate terminal, with the virtual environment
activated in each terminal.

### 1. Start the Kafka producer

``` powershell
python producer/weather_producer.py
```

The producer reads the city coordinate file, requests weather data from
Open-Meteo, and publishes weather events to the `weather_data` Kafka
topic.

### 2. Start the data processor / Kafka consumer

``` powershell
python data_Processing/process_weather.py
```

The processor consumes events, validates and transforms records,
calculates city-level temperature summaries, and inserts valid records
into PostgreSQL. It may also append processed records to
`data/processed_weather.csv`.

### 3. Start the dashboard

``` powershell
streamlit run dashboard/app.py
```

Open the local address printed by Streamlit in your browser. The default
address is usually:

``` text
http://localhost:8501
```

The dashboard reads records from PostgreSQL. It includes city filters,
summary KPIs, temperature and humidity charts, a wind-versus-temperature
chart, temperature-category distribution, and a records table.

## Dashboard Features

-   **Weather overview:** total records in the loaded dataset, selected
    city count, average temperature, and average humidity.
-   **Temperature analytics:** average temperature by city and
    temperature trends over time.
-   **Humidity and wind analytics:** average humidity by city and wind
    speed versus temperature.
-   **Temperature categories:** distribution of cold, moderate, warm,
    and very hot records.
-   **City filter:** select which cities to display.
-   **Weather records:** inspect the underlying records loaded from
    PostgreSQL.
-   **Refresh:** clear the Streamlit data cache and reload the dashboard
    data.

The current dashboard query loads up to the latest 10,000 records.
Therefore, its KPIs and charts describe the loaded and selected records,
not necessarily the entire database.

## Performance Evaluation

The project focuses on these five dimensions:

  -----------------------------------------------------------------------
  Measure                 Meaning                 Possible evaluation
  ----------------------- ----------------------- -----------------------
  Throughput              Number of records       Processed records
                          processed per unit of   divided by measured
                          time                    processing time

  Latency                 Time between event      Difference between
                          creation and processing `produced_at` and the
                                                  consumer processing
                                                  time

  Scalability             Ability to handle       Increase city count or
                          increased workload      event volume and
                                                  compare performance

  Reliability             Ability to process      Compare successful
                          events successfully     processing and
                                                  technical failures

  Accuracy                Quality of the          Track valid records and
                          collected and validated rejected records
                          data                    against validation
                                                  rules
  -----------------------------------------------------------------------

Be clear about the measurement method when reporting results. For
example, processing-batch throughput is not automatically the same as
sustained end-to-end system throughput. Invalid data rejected by
validation should also be distinguished from technical processing
failures.

## Troubleshooting

### Kafka connection error

-   Confirm that the Kafka broker is running.
-   Confirm that the broker is reachable at `localhost:9092`.
-   Check that the producer and consumer use the same topic name:
    `weather_data`.

### PostgreSQL connection error

-   Confirm that PostgreSQL is running.
-   Check the database name, username, password, host, and port in
    `.env`.
-   Confirm that the `weather_analytics` database exists.

### Python module not found

Activate the project's virtual environment and install the dependencies:

``` powershell
.\venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
```

### No records appear in the dashboard

-   Check that the producer is publishing events.
-   Check that the consumer is running without errors.
-   Run `SELECT COUNT(*) FROM weather_records;` in PostgreSQL.
-   Confirm that the dashboard uses the same database settings in
    `.env`.
-   Use the dashboard's refresh button to reload cached data.

### Open-Meteo returns HTTP 429

This response indicates that the request has been rate-limited. Do not
repeatedly restart the producer. Respect the `Retry-After` response
header when present, reduce request frequency or the number of
locations, and review the API's usage guidance.
